# 第三阶段暂停盘点与问题集中报告（2026-08-25）

## 1. 当前结论

本阶段已经把“小型长期记忆系统 demo”推进到一个明确的分界点：

- 数据导入、Source 分片、Episode/Concept 自动提取、float32 embedding、SQLite 持久化、RAM 暴力检索、静态 Association 遍历、证据约束回答和 Telegram 查询入口均已有可运行实现。
- 三道深度题需要的原文证据已经进入正式基线数据库，数据库审计无重复 Episode、无时间环、embedding 全部为 1024 维 float32。
- “纯向量 + 原子多查询”和“静态图”已经分别在三道题上命中过严格证据闭环；但尚未完成一个当前代码版本下的完整 3 题 × 3 模式最终验收。
- 最核心的未解决问题是 `graph_growing`：宽松时能增长但会写入错误身份或跨事件强因果；严格双审计后不会污染数据库，但可能一条关系也不写，失去“自主增长”的验证价值。

因此，当前状态不应描述成“整个 demo 已完成”，也不应描述成“检索仍不可用”。更准确的状态是：

> 数据与检索主链已得到实证；安全、持续且有用的 Association 自主增长仍未闭环。

本报告完成后暂停外部模型调用与继续修改，等待开发方向确认。

## 3. 已实现的系统能力

### 3.1 输入兼容与原文证据

- 支持 `.txt` 和 JSON。
- 蔚蓝档案适配器清洗多语言文本并保留原始人物标记。
- `source_key` 保存相对文件名，如 `main/33070.json`；Source 表仍只保存 `id + raw_text`。
- 修复了 `ScriptKr` 发言者识别：扫描同一记录的全部命令，优先选择真正含对白的命令，避免把立绘槽位更新误当说话者。
- Episode 可经 `source_id` 读取不太长的原始 Source 证据片段。

### 3.2 Episode 提取与审计

Episode 当前提示词的核心：

- 一个 Episode 是一个可独立回想的事件阶段，不是逐句对白摘要。
- 同一时间、地点、目标和连续互动应合并。
- 回忆、倒叙和当前场景必须拆开，并保留“据某角色说法”的证据状态。
- 区分曾见过、知道存在、建立联系和正式认识。
- 未知说话者保持 `???`、`[USERNAME]` 或“未标注发言者”，不得猜身份。
- 中文通常 80—300 字、15—30 条短对白通常 3—6 个 Episode，均为软范围。
- 提取后另有时间边界审计、粒度审计和证据修订。

### 3.3 Concept 与 Association

- Concept 包含人物、实体、地点、命名物品、持续状态、情绪、创伤、关系或抽象主题。
- 普通 Episode 通常提取 2—6 个 Concept，允许 0 个，不为凑数制造泛节点。
- Concept 支持多语言 alias、embedding_text、置信度、active/merged 状态与 canonical 指向。
- Association 已拥有 `relation_type`、`relation_key`、自然语言 `relation_text`、polarity、weight、confidence、evidence_count、use_count 等字段。
- 删除、时间线人工校正、Concept/Association 人工操作和日志均已有命令或程序入口。

### 3.4 查询链

当前代码配置：

```text
episode_top_k = 40
concept_top_k = 20
candidate_limit = 600
answer_episode_limit = 30
answer_concept_limit = 20
answer_path_limit = 24
graph_beam_width = 20
graph_max_hops = 3
growth_max_rounds = 2
```

当前查询流程：

1. LLM 把问题解析成 2—4 个原子证据问题。
2. 完整问题和原子问题分别进行 Episode/Concept 向量搜索。
3. 使用近似 RRF（`k=60`）融合，而不是让在多个泛查询中重复出现的节点单纯覆盖专门证据。
4. 完整问题保留 Top 10 综合锚点。
5. 每个原子问题按轮询方式最多保留 Top 6，避免一个子问题吃光全部证据槽。
6. 最终 30 条 Episode 中，原子锚点最多占约 3/4，剩余预算留给图路径端点。
7. 可生成最多 4 个下一跳检索问题。
8. 静态图最多遍历 3 跳；动态图最多增长 2 轮。
9. 回答后进行事实/推论审计；强因果问题再做独立的跨事件连续性审计，最多完整重写 3 次。

### 3.5 动态增长写入门

当前代码头版本为：

`v3.19_safe_historical_growth`

写入流程已经改为 fail-closed：

1. DeepSeek V3.2 生成候选 Association。
2. DeepSeek 做第一次证据审计。
3. 只有首审通过的候选，才交给 GLM-4.5V 做对抗复核。
4. 两次都 `accept=true` 才允许写入 SQLite。
5. 任一次失败、格式异常、缺审计项或网络失败都不写入。

双审计已由回归测试证明能够挡住“首审误放、复审发现身份幻觉”的关系。

### 4.3 古圣堂袭击因果链

要求闭环：

`33070 日奈分析爆炸 → 33070 阿里乌斯现场兵力/归责 → 32170 未花支援阿里乌斯/把其作为政变工具`

同时必须区分：

- 明确事实：阿里乌斯是现场执行势力。
- 明确事实：未花曾支援阿里乌斯，并将其纳入政变构想。
- 受限推论：较早政治支援可能构成背景。
- 未知：未花是否为古圣堂现场提供了具体路线、权限、爆破安排或仍生效的待命命令。

v3.17 的结果：

- vector_only：严格通过，0 次重写。
- graph_static：严格通过，0 次重写。
- graph_growing：最终答案审计通过，但证据压缩丢失 #307/#309，并写入了错误增长边，因此不通过。

v3.19 的 graph_growing：

- #320 与 #341 被保留，现场执行者证据存在。
- #307/#309 未进入最终 30 条；答案改用 #293/#295 说明未花是叛徒并曾下待命命令。
- 最终答案经 2 次重写后通过证据审计，并明确本次具体渗透机制未知。
- 4 条增长候选全部被审计拒绝，新增 Association 为 0。
- 严格自动评分为 0/1：缺少指定的 #307/#309 证据组，同时 graph_growing 没有产生并使用新边。

这里最有价值的结论不是某个提示词版本号，而是三个不同层次必须分开：

1. **召回层**：相关 Episode 是否进入 600 条候选。
2. **证据压缩层**：关键 Episode 是否进入最终 30 条。
3. **增长写入层**：候选边是否值得永久写库。

此前多次失败并不是 embedding 没找到证据，而是第 2 或第 3 层失败。

## 6. 当前集中问题

### 问题 A：增长模型和回答模型共用同一种 30 条选证预算

当前增长阶段调用 `_select_answer_evidence(..., episode_limit=30)`。为给图路径留空间，原子锚点只占约 22 条。v3.19 中 #307/#309 的排名靠后，结果是：

- 它们可在纯向量最终结果中出现；
- 但没有同时进入增长模型看到的节点集；
- 提示词即使要求先建 `#309 → #307 role_evidence_bridge`，模型也无证据可用。

可能修复：为增长单独使用 40—50 条证据，或按“答案事实槽”强制保留节点；回答仍保持 30 条，避免上下文无限扩大。

### 问题 B：自主增长的安全与活性冲突

已经观察到的危险边包括：

- 把导弹发射事实和日奈的预埋炸药假说合并成“解释了爆炸规模”。
- 把真琴误称为“茶会高层”。
- 把 `32170` 里较早的待命命令说成 `33070` 古圣堂渗透成功的具体防御缺口。
- 把“知道政变/与阿里乌斯串通”扩写成未被端点支持的资源、时机或现场支持。

双审计能防止这些边写入，但可能让增长归零。需要确定 demo 更偏向哪种验收：

- “宁可零增长也绝不写错”；或
- “允许低置信度、明确标注模糊的历史联想写入，等待后续交互强化/否定”。

### 问题 C：自动评分是否应该绑定具体 Episode ID

当前 Q3 要求必须命中 #307 或 #309。v3.19 最终答案使用 #293/#295，也能证明未花是茶会成员/叛徒并曾下令待命，但不能证明她把阿里乌斯当政变工具，因此严格判失败是有理由的。

另一方面，不同重新提取版本可能产生语义等价但 ID 不同的 Episode。长期看，评分器最好同时支持：

- 固定 Episode ID 组；
- source_key；
- 必需事实槽的 LLM/规则审计；
- 禁止的强因果声明。

### 问题 D：用户问题自身包含比文本更强的因果前提

问题写“他们之所以能成功渗透，是因为哪位茶会高层的暗中协助”，但当前文件证据只稳固支持：未花较早支援阿里乌斯、将其视为政变工具；并不明确证明她为古圣堂当日渗透提供具体协助。

当前系统选择指出这一不确定性，而不是顺从问题前提。这与此前“资料不足时直接说明”的目标一致，但需要确认是否继续采用这个严格标准。

### 问题 E：资产元数据已落后于代码头

- `README.md` 目前更新到 v3.15 附近。
- `validation/stage3-deep-evidence-manifest.json` 仍记录 `atomic_episode_anchors_per_query = 2` 和 v3.15。
- 当前代码实际为完整问题 Top 10、原子问题 Top 6 轮询、v3.19 双审计。
- 项目目录不是 Git repository，无法用 commit/tag 固定每次实验代码状态；目前只能依靠 prompt_version、日志和隔离评测目录追踪。

## 8. 需要开发者确认的决策

### 决策 1：Association 增长的容错方向

建议：允许低置信度的 `historical_support_context`，但禁止任何未证实的具体机制、身份和资源描述。即“可以模糊地有关系，不能具体地说错”。

请确认是否接受。

### 决策 2：安全无增长是否算一次合格行为

建议分成两个指标：

- `answer_passed`：答案证据闭环是否通过。
- `growth_passed`：是否新增/强化了至少一条正确且被使用的边。

零增长时前者可以通过，后者失败；不要把整个查询简单记成一个布尔值。

请确认是否采用。

### 决策 3：是否扩大增长上下文到 40—50 个 Episode

建议先设 40，只扩大增长阶段，不扩大最终回答阶段。32 GiB RAM 不是瓶颈，主要代价是 LLM 输入和候选关系判断复杂度。

请确认 40 是否可接受，还是希望直接 50。

### 决策 4：对问题前提保持何种态度

建议继续保持当前严格策略：问题即使暗示强因果，证据只能支持政治背景时，必须说“可能相关，具体机制未知”。

请确认。

### 决策 5：下一轮是继续 Q3，还是先冻结并整理工程资产

两个选择：

- A：先解决 Q3 安全增长，再跑完整 9 组。
- B：先补 README、manifest、清理历史评测目录并建立 Git，再继续实验。

建议 A；因为当前最有价值的未知仍是 Association 是否能安全自主增长。完成闭环后再整理版本，更容易确定真正的稳定基线。

## 12. v3.20 实现内容

### 12.1 增长证据使用独立预算

回答仍最多使用 30 条 Episode，但增长阶段改为独立最多 40 条 Episode：

```text
answer_episode_limit = 30
growth_episode_limit = 40
```

完整问题保留前 10 个 Episode 锚点，每个原子问题轮询保留前 6 个锚点。Q3 两轮增长输入都同时包含：

```text
#307  未花暗中支援阿里乌斯
#309  阿里乌斯是政变工具；未花要让渚下台
#320  巡航导弹不足以解释古圣堂爆炸规模
#341  现场确认阿里乌斯分校兵力与地下墓穴潜入推测
#139  阿里乌斯小队的现场作战指令
```

这证明 v3.19 的零增长主要不是模型不会连接，而是 30 条统一压缩预算在进入增长模型前丢掉了 #307/#309。

### 12.2 Association 增加结构化可信度与来源

schema v2 为 Association 增加：

```text
claim_level
    direct_fact
    supported_inference
    historical_context

audit_status
    not_required
    dual_accepted

evidence_json
    两端 type / id / source_key / Episode 文本快照

audit_json
    主审与对抗审计的接受结果和理由
```

强化已有关系时合并 evidence/audit 记录；弱推论不能覆盖已有直接事实，`dual_accepted` 不会在强化时丢失。

### 12.3 双模型 fail-closed 写入门

查询增长候选先由 DeepSeek-V3.2 主审，再由 GLM-4.5V 以对抗方式复核。任一模型拒绝、响应无效或调用最终失败都不写库。此次完整增长运行：

| 问题 | 两轮候选 | 双审计接受 | 实际新建 | 强化 | 硬规则拒绝 |
|---|---:|---:|---:|---:|---:|
| 补习部真正目的 | 7 | 7 | 3 | 1 | 0 |
| 乐园悖论与高层偏执 | 9 | 5 | 5 | 0 | 0 |
| 古圣堂袭击因果链 | 8 | 3 | 2 | 0 | 1 |
| 合计 | 24 | 15 | 10 | 1 | 1 |

双审计接受但未产生写入的其余候选为已存在/同轮重复关系，不会制造重复边。

### 12.4 确定性跨事件因果门卫

LLM 双审计仍可能共同接受不合适的关系。因此增加不可由模型绕过的规则：

- 跨 Source 的 `political_precondition` 一律拒绝，必须降级成 `historical_support_context`；
- 历史背景关系必须明确写出：没有证据证明它延续到、促成或提供资源给后续具体行动；
- 早期“待命/准备”不能变成后续事件的渗透机制；
- 现场对预埋炸药的怀疑不能升级成已确认事实；
- 问题前提不能补成 Episode 没有表达的具体机制。

实测中，DeepSeek 和 GLM 都接受了一条 `#309 未花政变 → #325 真琴串通` 的跨来源 `political_precondition`，但确定性门卫仍将其拒绝并写日志。这说明硬规则不是重复保险，而是实际必要的第三道门。

### 12.5 评测源数据库真正只读

最终冻结检查发现：旧 CLI 会在进入 `evaluate` 分支前构造 `MemoryApplication`，从而对正式基线执行 schema 初始化/迁移。它没有写入查询边或改变 1,825 条 Association 的内容，但把基线从 schema v1 迁移到了 v2。

已修复为：

```text
CLI 识别 evaluate
→ 不构造源库 MemoryApplication
→ SQLite mode=ro 打开源库
→ backup 到各模式副本
→ 只在副本中初始化/迁移/增长
```

Windows 下源、目标连接均显式 `close()`；新增两个回归测试覆盖“CLI 不初始化源应用”和“备份不迁移 v1 源 schema”。当前正式基线保留为内容干净的 schema v2，不做高风险、无收益的破坏性降级。

## 15. 尚未解决但不需要当前产品决策的问题

目前没有必须由开发者提供意见才能继续的技术阻塞。剩余问题适合通过扩大实验而不是主观定阈值解决：

1. **回答模型仍会强化问题前提。** Q3 三种模式都需要一次重写。短期审计可控；长期可考虑先生成结构化 claim，再由确定性模板渲染事实/推论/未知，减少反复调用。
2. **双模型可能共同犯错。** 本轮已有实证，必须继续扩充 relation-specific 硬规则，不能把“双接受”当作事实保证。
3. **增长边仍偏局部和冗余。** Q1 的部分边只是相邻 Episode 的语义承接。需要用后续查询复用率、最短路径缩短量和答案贡献度评估长期价值，而不是只看成功写入数。
4. **证据快照会增加数据库体积。** 当前规模可以接受；全量运行前应实测 `evidence_json/audit_json` 的增长速度，再决定是否改为独立审计表或压缩日志引用。
5. **Episode 修订后的快照一致性。** 关系中的 evidence 文本是建立时快照；若人工修改 Episode，需要标记该 Association 待复核。
6. **供应端尾延迟。** 本轮出现一次 300 秒 read timeout，自动重试成功。它不影响正确性，但会显著放大完整评测耗时。
7. **尚未验证长期网络稳定性。** 9/9 是固定小题集结果，不代表在全量剧情和数百次连续查询后仍不会产生路径漂移、边爆炸或错误强化。

下一阶段的优先工作应是：在正式基线副本上进行多轮、多问题连续增长 soak test，记录每条边的创建、复用、强化、拒绝和对答案的真实贡献；暂时不需要引入 ANN、float8、记忆衰减或新的专家系统表。
