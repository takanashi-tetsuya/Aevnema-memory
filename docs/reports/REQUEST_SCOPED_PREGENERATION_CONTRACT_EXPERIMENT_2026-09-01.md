# 请求级生成前合同实验报告

日期：2026-09-01  
状态：实验实现完成；尚未接入 `chat_bot` 生产回答链路

## 1. 实验目的

本阶段验证一个比“回答生成后再审计、再修复”更短的方案：在回答生成前，把本轮可以陈述的事实、动作结果、问题前提和限制编译成一个不可变请求快照，让快速模型只负责语言渲染。

重点不是给模型增加更多领域规则，而是解决四类通用错误：

1. 用户要求写入后，模型在数据库实际写入前就声称“已经记住”；
2. 另一个请求、用户或目标空间的回执泄漏到当前回答；
3. 异步回执在回答快照生成之后才到达，却被当前回答观察到；
4. 用户问题中的前提尚未得到证据支持，模型却把前提当成事实继续推导。

本实验没有修改生产数据库，没有写入真实私人、公共或剧情记忆，没有运行 embedding，也没有为 embedding 配置 fallback。

## 2. 专有名词

### 2.1 RequestAnswerContract

一次用户请求在“准备生成回答”时看到的不可变语义快照。它包含本轮问题、请求动作、允许陈述的事实、限制、待写内容、动作回执和问题前提。

不可变的含义是：任何后续变化都会产生一个新对象，已经交给渲染器的旧对象不会被悄悄修改。

### 2.2 RuntimeReceipt

执行器对本轮动作给出的机器可验证回执。关键字段为：

- `request_id`：回执属于哪一次请求；
- `action`：执行了什么动作；
- `target`：动作的精确目标；
- `status`：`succeeded`、`failed` 或 `cancelled`；
- `result_summary`：成功结果的公开摘要；
- `error_summary`：失败或取消原因的公开摘要。

只有 `request_id + action + target` 精确匹配当前请求的回执才能参与回答。错误目标的回执被隔离，其他请求的回执直接拒绝。

### 2.3 QuestionPremise

用户问题中隐含但尚未必然为真的前提。状态分为：

- `supported`：允许肯定；
- `contradicted`：只允许否定，替代事实仍需独立证据；
- `unresolved`：既不能肯定也不能否定，只能说明目前无法确认。

### 2.4 VerifiedActionOutcome

程序根据请求动作和精确匹配回执确定性编译出的动作状态。没有匹配回执时状态是 `unverified`，不允许模型自行解释为成功、失败、取消或已经尝试。

### 2.5 ResponseDirective

生成器必须表达的最小语义单元。它由程序从动作结果、支持事实、限制和问题前提编译，而不是由回答模型自由规划。

模型可以改变语气和语序，但不能遗漏必答单元、改变动作状态、增加错误原因或加入清单外世界事实。

### 2.6 快照边界

回执在快照形成前到达，新快照可以看到它；回执在快照形成后到达，当前回答仍使用旧快照，只能在下一次快照中看到它。这使异步执行结果具有明确的可见性边界。

## 3. 最终架构

```text
用户请求
  ↓
请求动作 + 事实槽 + 问题前提
  ↓
执行器产生 RuntimeReceipt
  ↓
精确匹配 request_id / action / target
  ├─ 外来 request_id：拒绝
  ├─ 错误 target：隔离
  └─ 正确回执：进入当前快照
  ↓
VerifiedActionOutcome
  ↓
ResponseDirective
  ↓
Qwen 仅做自然语言渲染
  ↓
高风险场景可选原子主张审计
```

线上正常路径仍只有一次回答模型调用。实验中的 Qwen 盲审和 DeepSeek 原子审计是离线评测，不应加入所有 light 请求。

## 5. 测试集合

16 个案例覆盖：

- 写入成功、失败和无回执；
- 错目标回执和外来请求回执；
- 快照前、快照后到达的迟到回执；
- 检索成功且有事实、检索成功但无事实、检索失败；
- 外部动作被取消；
- 问题前提已支持、未决和被否定；
- 同一请求中一个动作成功、另一个动作失败；
- 正确回执旁混入错目标回执。

测试内容使用 ALPHA 至 THETA、蓝塔、林和周等虚构标记，不依赖蔚蓝档案专名和剧情规则。

## 6. 演进过程

### v1-v3：直接把合同交给模型

模型会把“没有回执”扩写成“系统没有反馈”，或把当前帮助意愿说成底层系统已经准备好。DeepSeek 批量审计还出现超时，说明单纯增加审计并不能缩短线上路径。

### v4：确定性动作结果

程序先编译 `VerifiedActionOutcome`，请求级生成平均约 1.43 秒，但原子审计只通过 9/16。主要问题是模型仍会添加比喻、原因、承诺和额外角色化事实。

### v5-v6：必答语义单元

引入 `ResponseDirective` 后，针对失败案例达到 7/7 独立安全审计。关键结论是“允许模型说什么”不够，还必须明确“哪些单元一定要说，并且不能加入其他单元”。

### v7：生成和审计共享合同

此前生成器看到 `response_directives`，审计器却只看到回执和限制，造成审计接口信息损失。v7 让两者共享 `requested_actions` 和 `response_directives`，完整集原子审计从 9/16 提升到 14/16。

### v8：取消自由过渡状态

最后两个失败案例来自“已收到标记/指令”一类不必要过渡状态。v8 要求 `unverified` 直接说明“尚未实际执行、无法确认结果”，不再自行叙述接收、接受或准备状态。

## 7. 最终结果

最终同版本运行：`validation/request-scoped-generation-v8-full-20260901/results.json`。

| 指标 | 控制组 | 请求级 v8 |
|---|---:|---:|
| 案例数 | 16 | 16 |
| 生成成功 | 15/16 | 16/16 |
| 平均生成时间 | 1.902 秒 | 1.679 秒 |
| 中位生成时间 | 1.239 秒 | 1.562 秒 |
| 最大生成时间 | 8.895 秒 | 3.450 秒 |
| 超时 | 0 | 0 |
| Qwen 盲审完成数 | 15 | 15 |
| Qwen 盲审通过 | 14/15 | 15/15 |

控制组有一条回答没有返回合法 JSON，因此该条没有进入成对盲审。Qwen 同时担任生成器和盲审员，存在同模型偏差，只用于检查任务保留与自然度，不能作为最终安全结论。

请求级 v8 随后由 Qwen 抽取原子主张、DeepSeek 映射合同范围：

- 16/16 通过；
- 0 抽取错误；
- 0 Scope 错误；
- 0 误放行；
- 0 误拦截。

同批控制组只有 15 条可审计回答，其中 10/15 通过同一原子范围判定。该数字反映“是否符合当前合同审计器”，不等同于人工事实正确率；清单中的人工标签原本统一标为安全，因此报告不把它冒充真实人工安全评测。

确定性层同时得到：

- 1 个外来请求回执被拒绝；
- 2 个错目标回执被隔离；
- 100 个并行请求没有回执串线；
- 快照后到达的回执不会改变旧快照；
- 25 个相关本地测试全部通过。

## 8. 已验证结论

1. 动作真实性应由执行器回执决定，不能交给回答模型推断。
2. 请求级不可变快照可以解决并发串线和迟到回执可见性问题，不需要共享可变配置和全局大锁。
3. 问题前提应作为独立状态保存，不能混入支持事实。
4. 程序编译必答语义单元，比继续增加回答后修复规则更短、更稳定。
5. 快速 Qwen 可以在约 1.7 秒平均时间内渲染该合同；完整 DeepSeek 审计适合离线和高风险请求，不适合所有 light 对话。
6. 这套机制是领域无关的请求协议，不含“老师、会长、蔚蓝档案”等剧情硬编码。

## 9. 尚未解决的问题

### 9.1 动作缺少面向用户的摘要

当前 `RequestedAction` 只有内部 `action` 和 `target`。模型曾把 `knowledge_recall` 渲染成“回忆”，这在事实状态上正确，但不一定是最自然的产品措辞。

生产接入前应增加由调用方提供的 `public_action_summary`，例如“检索蓝塔顶层的剧情资料”。回答模型只能转述该摘要，不能自行解释内部动作代码。

### 9.2 Limitation 仍是无类型自由文本

`limitations` 目前不能绑定到具体动作或事实槽。写入失败时，`failed receipt` 已证明失败，而“成功写入状态” limitation 又要求表达无法确认，两个单元可能产生重复或措辞冲突。

下一步应把 limitation 改成带 `slot_id`、`action_ref` 或 `claim_ref` 的结构，并在回执解决对应槽后由程序移除，而不是让模型消解冲突。

### 9.3 待写内容不应以内部字段名暴露给渲染器

模型曾说“已作为创意内容进入本轮回答”，说明 `creative_private_items` 的字段语义影响了表述。应把动作对象并入公开动作摘要，渲染器不再看到内部持久化分类名。

### 9.4 样本规模仍小

16 个案例证明了机制可行，不证明跨语言、长回答、多工具并发和真实 Telegram 对话都稳定。至少还需增加：

- 中英日韩混合动作摘要；
- 多个同 action、不同 target 的并行动作；
- 部分成功、重试成功、重复回执和乱序回执；
- 用户在工具执行中取消请求；
- 剧情事实、私人创作和公共事实同时出现的真实回答。

## 10. 生产接入建议

暂不把完整 DeepSeek 审计放进所有请求。推荐顺序：

1. 在 `chat_bot` 的工具执行层产生 `RuntimeReceipt`；
2. 为每个动作增加 `public_action_summary`；
3. 把 limitation 结构化并绑定事实槽或动作；
4. 在最终回答前冻结 `RequestAnswerContract`；
5. light/standard 使用一次 Qwen 合同渲染；
6. 只有知识库写入、外部发送、前提冲突和高 generation 推论进入原子审计；
7. 线上记录合同版本、回执 ID、快照时间和渲染版本，但不记录其他用户的回执正文。

本阶段结论是：请求级生成前合同已具备继续接入的技术价值，但应先完成动作公开摘要和结构化 limitation，避免靠更长提示词掩盖接口缺口。
