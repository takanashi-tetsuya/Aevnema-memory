# 联想式长期记忆系统：架构设计、术语定义与实验综合报告

**报告日期：** 2026-08-26  
**当前实验版本：** Stage 5 / `stage5-causality-v1`  
**分析修订：** `stage5-analysis-v1.1`  
**适用读者：** 项目作者、未来维护者、希望复现实验的开发者  
**报告性质：** 已实现系统与已执行实验的综合说明；不是尚未执行的计划书

---

## 1. 摘要：这个系统在做什么，目前证明了什么

本项目试图实现一种可持续生长的长期记忆系统。它不只把文本切块后做向量搜索，还希望把每次阅读、查询和推理中发现的关系保存为可复用的 `Association`，让以后遇到相关问题时能够沿着旧关系继续联想。

系统的主链是：

```text
JSON / TXT 原始剧情
        ↓
清洗、保留多语言与人物标记
        ↓
Source：长度适中的原文证据片段
        ↓
Episode：可独立回想的事件或状态
Concept：人物、组织、地点、情绪、主题等概念
        ↓
float32 Embedding + SQLite 持久化
        ↓
Episode/Concept 向量召回
        ↓
Association 图遍历与查询期自主增长
        ↓
Source 原文回查、受证据约束的回答与审计
```

截至 Stage 5，已经得到以下结论：

1. **数据主链已经跑通。** JSON/TXT 可以转换成 Source，自动提取 Episode/Concept，生成 1024 维 `float32` embedding，并写入 SQLite。
2. **当前小规模下，float32 CPU 暴力检索足够。** 100 万条、1024 维向量的实测平均查询约 86.31 ms；远端 LLM 调用远比本地向量运算慢。
3. **复杂多跳问题能够回答。** Stage 4 的 7 道封闭语料问题在五种检索设置下都达到语义 7/7；精确 Episode 组覆盖存在差异。
4. **Association 可以安全增长并立即参与后续查询。** 新边需要两个模型分别审计，任何异常都不写库；Stage 5 的安全审计全部通过。
5. **Association 的“被使用”不等于“带来收益”。** Stage 5 中，Q1 新边在 10 次处理组的 7 次 Q2 路径里被复用，但对预注册的 Q2 `Recall@30` 没有一次产生增益。
6. **目前的主要问题已从“能否召回”转移到“如何分配最终证据槽”。** Q2 的 8 组正确证据在 600 条候选中每次都找齐，但其中一组经常在压缩到最终 30 条时被裁掉。

最准确的当前判断是：

> 系统已经具备可审计的关联生长和路径复用能力，但尚未证明这些新关联对后续问题存在稳定、可测的边际贡献。下一步应优先改进证据分配与边际贡献评估，而不是单纯增加边数。

## 2. 项目目标与边界

### 2.1 长期目标

最终目标不是制作一个只适用于《蔚蓝档案》的问答专家系统，而是验证一种更一般的“联想式记忆”机制：

- 从用户对话、剧情、笔记等原始材料中形成事件记忆；
- 保存人物、事物、情绪、关系和抽象主题；
- 新材料可以唤起旧记忆；
- 查询和对话可以形成新的 Association；
- 后续交流可以确认、修正或否定旧理解；
- 系统必须能说明自己掌握了什么证据、做了什么推论、还不知道什么。

这更接近：

```text
episodic memory（情景记忆）
+ concept/entity graph（概念/实体图）
+ vector retrieval（向量检索）
+ association graph（联想图）
+ evidence audit（证据审计）
```

### 2.2 当前 demo 的验证目标

当前阶段重点验证四件事：

1. 能否从复杂、多语言、非统一格式的文本中提取可用 Episode；
2. 能否从远距离、跨文件的片段中重建多跳证据链；
3. 能否在查询过程中自主产生 Association，并让它立即参与检索；
4. 这些 Association 是否能在后续问题中真正改善证据覆盖，而不只是让图变大。

### 2.3 当前不追求的内容

当前没有把以下内容作为 Stage 5 的主要任务：

- 高并发或低延迟 Telegram 服务；
- GPU 检索；
- 百万级真实数据的长期运行；
- ANN 向量数据库；
- embedding 模型升级与多版本迁移；
- 联网补充剧情；
- 完整的遗忘、衰减、冻结、恢复策略；
- 自动把所有模糊 Concept 立即合并；
- 用写边数量作为成功指标。

这些都可以发展，但应建立在当前因果机制已经被验证的基础上。

## 3. 专有名词与核心概念定义

本节是项目的统一词汇表。未来代码、报告和讨论应尽量沿用这些含义。

### 3.1 数据表示术语

#### Source（原文证据片段）

`Source` 是系统保存的原始材料片段。它不是摘要，而是日后可以回查的证据。

当前 Source 表只保存：

```text
id       数据库自动分配 ID
raw_text 清洗和分片后的原始文本
```

一个长文件会被切成多个 Source。Source 不负责表示“这是同一个文件的第几块”；这些导入上下文放在 Episode 和提取任务里。

#### source_id

`source_id` 是 Episode 指向 Source 的数据库外键。它解决的是：

> 这条 Episode 的原文证据存在哪里？

回答、审计和人工检查都可以通过它回读原文。

#### source_key

`source_key` 是输入语料中的逻辑文件名，例如：

```text
main/33070.json
event/10038/1003805.json
```

它不是本机绝对路径。它用来保留文件所属模块、编号和可能的剧情顺序信息，并使不同电脑上的实验仍可比较。

#### Episode（情景记忆）

`Episode` 是可独立理解、可被回想的一段事件、状态或情景。它不是任意固定长度的切块，也不是逐句对白摘要。

一个合格 Episode 通常应满足：

- 有一个主要事件、状态或认知变化；
- 尽量自包含，减少“她”“那里”等无法独立解析的指代；
- 保留人物、目标、地点、时间和证据强度；
- 当前事件与回忆/倒叙分开；
- 角色说法不能自动升级成客观事实；
- 可以与同一 Source 中的其他 Episode 重叠。

例如原文“她跑过去了”不适合独立 embedding；“阿洛娜看到老师回来后，高兴地跑向老师”更适合作为 Episode。

#### Concept（概念）

`Concept` 是自然语言中可被联想到的东西，范围故意比传统知识图谱的“实体”更宽：

- 人物：阿鲁、日富美；
- 组织：便利屋 68、茶会；
- 地点：古圣堂、黑市；
- 物品：佩罗罗周边、巡航导弹；
- 状态或行为：喝醉、被驱逐；
- 情绪或心理：猜忌、创伤、害怕被遗忘；
- 关系或主题：师生关系、政治排外、乐园悖论。

Concept 支持多个语言和别名，也允许先保留模糊性，再由后续证据确认或合并。

#### canonical concept（规范概念）

多个名称被确认指向同一概念时，保留一个主 Concept，其他 Concept 可以标记为 `merged` 并通过 `canonical_concept_id` 指向它。这样既保留历史，又避免查询时无限重复。

#### alias（别名）

同一 Concept 的不同名字、语言或称呼，例如：

```text
日富美 / Hifumi / ヒフミ
浮士德 / Faust
```

别名并不天然证明身份相同；别名合并仍需上下文和模型判断。

#### Association（联想关系）

`Association` 是两个 Episode/Concept 节点之间的有向、带类型关系。它可以表示：

```text
Episode → Episode
Episode → Concept
Concept → Episode
Concept → Concept
```

它不是“事实表”的简单替代，而是检索时可以沿着走的联想路径。边可以很强，也可以只是弱提示。

#### node / edge（节点 / 边）

- `node`：Episode 或 Concept；
- `edge`：一条 Association；
- `from` / `to`：边的起点和终点；
- 有向边表示联想方向，不必自动理解为强因果。

#### relation_type（关系类型）

关系的大类。当前增长提示词允许的主要类型包括：

| 类型 | 含义 | 示例 |
|---|---|---|
| `temporal` | 时间先后或阶段关系 | 事件 A 早于事件 B |
| `causal` | 有证据支持的因果或促成关系 | 决策 A 导致行动 B |
| `identity` | 身份、化名、同一对象 | 浮士德是日富美的化名 |
| `semantic` | 主题或语义相关 | 乐园悖论与信任危机相关 |
| `co_occurrence` | 同场出现或共同被提及 | 两人在同一事件出现 |
| `recall_trigger` | 某事触发另一记忆 | 创伤情境唤起旧场景 |
| `interpersonal` | 人际关系 | 支援、敌对、师生关系 |

#### relation_key 与 relation_text

- `relation_key`：少量、机器可理解的稳定标签，例如 `historical_context`；
- `relation_text`：完整自然语言描述，保存这条关系究竟表达什么。

这种设计避免为了每种剧情关系建立新的表，同时又比单纯 `A—B` 更可解释。

#### polarity（极性）

关系是肯定、未知/中性还是否定：

```text
 1  肯定关系
 0  中性或未定
-1  否定关系
```

否定关系会保留，因为“不是同一个人”“并未发生”也属于重要记忆。

#### weight 与 confidence

- `weight`：这条边对联想传播的强度；弱边不代表错误，只代表它不应强烈主导路径。
- `confidence`：系统对关系内容正确性的信心。

两者不同。一个关系可以“很确定但联想作用很弱”，也可以“暂时不确定但很值得探索”。最终事实判断仍交给有原文证据的回答层。

#### evidence_count

支持某条关系的证据次数。后续材料再次确认时，可以增加而不是无条件建立重复边。

#### claim_level（主张强度）

当前三档为：

| 值 | 定义 |
|---|---|
| `direct_fact` | 端点原文明示的直接事实 |
| `supported_inference` | 多段证据共同支持、但不是一句原文直接说出的推论 |
| `historical_context` | 历史背景、主题铺垫或解释性上下文，不应冒充具体现场机制 |

#### provenance / evidence_json / audit_json（溯源信息）

- `evidence_json` 保存支持关系的端点、`source_key` 和文本快照；
- `audit_json` 保存模型审计结果和理由；
- `created_reason` 记录为什么创建；
- 时间戳、使用次数等用于追踪生命周期。

这些字段回答的是：

> 这条边从哪里来？当时为什么被接受？以后如何复查？

### 3.2 向量检索术语

#### Embedding（向量表示）

Embedding 是模型把文本转换成固定长度数字数组的结果。语义相近的文本通常在向量空间中更接近。

当前统一使用：

```text
模型      Pro/BAAI/bge-m3
维度      1024
磁盘类型  float32
内存类型  float32
每条大小  1024 × 4 = 4096 bytes
```

#### dimension（维度）

一个 embedding 中数字的个数。当前固定为 1024。不同维度或不同模型的向量不能直接混合计算。

#### dtype（数字类型）

`dtype` 表示每个数字如何存储。当前统一采用 `float32`，每个元素 4 字节。

早期曾讨论 float8 粗搜和 float16 精排，但最终没有采用，原因是 CPU/NumPy 对 float8 的实际矩阵乘法支持与转换成本不确定，而 32 GiB RAM 对当前 demo 和早期百万级估算仍可接受。

#### BLOB

SQLite 的二进制字段。NumPy `float32` 数组通过 `tobytes()` 写入 BLOB，通过 `np.frombuffer(..., dtype=np.float32)` 读取。它比 JSON/TEXT 更紧凑，也避免数字文本解析。

#### L2 normalization（L2 归一化）

把向量除以自身长度，使其范数等于 1：

```text
v_normalized = v / ||v||₂
```

归一化后，两个向量的余弦相似度可以直接用点积计算。当前建议在生成 embedding 后统一归一化并保存，避免每次搜索重复计算 norm。

#### cosine similarity（余弦相似度）

比较两个向量方向是否接近：

```text
cos(a,b) = (a · b) / (||a||₂ ||b||₂)
```

如果两者已经 L2 归一化，则简化为 `a @ b`。

#### brute-force search（暴力向量搜索）

让 query 向量与内存中的全部向量做矩阵乘法，再取 Top-K。优点是实现简单、结果精确、便于调试；缺点是数据极大时计算量线性增长。

#### ANN（Approximate Nearest Neighbor，近似最近邻）

通过专门索引快速找到“大概率接近”的向量，但可能漏掉真实最近邻。当前未引入，因为本地向量运算不是整体瓶颈，而且暴力搜索更适合建立可靠基线。

#### EmbeddingIndex（内存向量索引）

可重建的 RAM 加速结构。它保存平行数组：

```text
ids[i]        ↔ embeddings[i]
```

采用预分配的 `(capacity, dimension)` 数组、`count` 和倍增扩容，避免每次追加都复制整块矩阵。Episode 与 Concept 使用相同实现、不同实例。

#### source of truth（真实数据源）

SQLite 是持久化真实数据；RAM index 只是缓存。正确写入顺序是：

```text
先写 SQLite 并 commit
→ 获得数据库 ID
→ 再追加 RAM index
```

若程序在两步之间崩溃，下次可从 SQLite 重建 index。

### 3.3 检索与推理术语

#### QueryIntent（查询意图）

LLM 对用户问题的结构化解释，包括要找的人物、事件、时间边界、需要哪些证据槽，以及应该生成哪些原子查询。

#### atomic query（原子查询）

把一个复杂问题拆成一次只寻找一种证据的小问题。例如“古圣堂为什么既有象征意义又危险”可拆成：

```text
伊甸条约的政治目的是什么？
古圣堂的历史作用是什么？
会场的地下结构是什么状态？
袭击者如何部署？
哪些机制只是角色推测？
```

#### follow-up query（后续查询）

第一轮召回后，LLM 根据仍缺的证据槽产生的第二轮检索问题。它用于补齐远距离证据，而不是重复第一轮。

#### Top-K

按相似度或综合分数保留前 K 个结果。例如 `episode_top_k=40` 表示每次 Episode 搜索最多保留 40 个直接命中。

#### seed / anchor（种子 / 锚点）

- `seed`：图遍历的起始节点；
- `anchor`：为了保证某个原子问题不被其他查询淹没而优先保留的 Episode。

#### candidate set（候选集）

向量搜索、原子查询、follow-up 和图遍历合并后的较大集合。当前上限为 600。进入候选集只表示“系统找到了它”，不表示它最终会交给答案模型。

#### RRF（Reciprocal Rank Fusion，倒数排名融合）

一种合并多个排名列表的方法。当前使用近似形式，让在不同查询中排名靠前的结果得到加分，同时避免只比较不同查询之间不可直接校准的原始相似度。

常见形式为：

```text
score(d) = Σ 1 / (k + rank_i(d))
```

当前 `k≈60`，数值越高表示文档在多个列表中总体排名越好。

#### graph traversal（图遍历）

从检索命中的 Episode/Concept 出发，沿 Association 找相邻节点。它模拟“想到 A 后又想到 B”。当前最多 3 跳。

#### hop（跳）

沿一条 Association 从一个节点走到另一个节点叫一跳。三跳路径可能是：

```text
情侣菜单 Episode
→ 阿鲁 Concept
→ 便利屋 68 Concept
→ 圣三一支援 Episode
```

#### beam width（束宽）

图遍历时每一层最多保留多少条有希望的路径。当前 `graph_beam_width=20`，用于限制组合爆炸。

#### path / path score（路径 / 路径分数）

路径记录“系统为何从一个记忆联想到另一个记忆”。路径分数综合种子相关性、边权、置信度、跳数惩罚等，但它只用于排序，不等于最终事实置信度。

#### evidence allocation（证据分配）

从最多 600 条候选中挑选最终交给答案模型的 30 条 Episode 的过程。它是当前系统最重要的瓶颈。

#### Source excerpt（原文摘录）

最终 Episode 会附带对应 Source 的部分原文，用于防止 Episode 摘要遗漏邻近台词，支持答案审计。当前配置每条最多 3000 字符。

#### evidence group（证据组）

评测中，把表达同一事实的一个或多个等价 Episode 归为一组。例如 `[274,275]` 中任意一个被选中，都算覆盖“伊甸条约的政治目的”这一组。

#### Recall@30

最终 30 条 Episode 覆盖了多少预注册证据组：

```text
Recall@30 = 被覆盖证据组数 / 全部必需证据组数
```

Q2 有 8 组，因此 `7/8 = 0.875`。它衡量证据覆盖，不直接等同于答案文字质量。

### 3.4 增长、安全与实验术语

#### query-time growth（查询期增长）

系统在回答问题的过程中，利用当前检索到的证据提出新 Association，审计通过后立即写入数据库。它是“自主增长”的核心机制。

#### reinforcement（强化）

如果候选关系已经存在，系统不新建重复边，而是更新其权重、置信度、证据数和溯源。Stage 5 的隔离运行中没有发生强化，新增边均为 created。

#### dual audit（双模型审计）

一条新边先由 DeepSeek V3.2 做证据审计，再由 GLM-4.5V 做独立对抗复核；只有两者都接受才写入。

#### fail-closed（失败时关闭写入）

网络超时、JSON 不合格、审计缺失或任一模型拒绝时，默认不写边。这样宁可少学，也不把未审计关系持久化。

#### treatment / control（处理组 / 对照组）

- 处理组接受被研究的变化；
- 对照组不接受该变化；
- 其他条件尽量一致。

Stage 5 中，处理是“先让 Q1 增长 Association，再回答 Q2”。

#### masked arm（遮罩组）

从处理组数据库出发，但在读取时临时隐藏 Q1 新边，并把被强化的旧边恢复到 Q1 前状态。它构成一个反事实：

> 如果其他数据库状态相同，唯独看不见 Q1 学到的边，Q2 会怎样？

#### placebo arm（安慰剂组）

先让一个无关问题增长边，再回答 Q2。它用于区分“任何增长都会改变结果”与“特定 Q1 关系才有作用”。

#### ablation（消融）

有控制地移除某个模块、某类边或某一步骤，观察指标变化。它用于回答“这个部件是否真的有贡献”。

#### paired block（配对实验块）

同一个 block 内的 T/C/M/P 使用同一冻结起点和同一 replay 输入，然后比较差值。配对能减少不同 LLM 规划或不同随机条件带来的噪声。

#### pilot（预跑）

用于验证实验程序和发现设计错误的小规模运行。Pilot 不进入正式统计，避免看过结果后再改变规则造成偏差。

#### preregistration（预注册）

运行前冻结问题、证据组、主要指标、组别和比较方式。这样不会因为结果不好而事后更换成功标准。

#### replay bundle（确定性重放包）

保存一次 Q2 的结构化意图、原子/后续查询、float32 query embeddings、排名、锚点和配置。以后可以在不同 Association 视图上重放，不再调用 LLM。

#### deterministic replay（确定性重放）

四个组使用完全相同的查询规划和向量输入，只改变 Association 视图。它更适合判断图本身的因果作用。

#### end-to-end evaluation（端到端评测）

每个组独立调用 LLM 做规划、增长、回答和审计。它更接近真实使用，但结果也包含模型随机性、网络重试和答案生成波动。

#### ecological validity（生态有效性）

实验设置与真实使用场景有多接近。端到端层生态有效性更高；确定性 replay 的控制更严格。两者用途不同。

#### counterfactual（反事实）

保持其他条件尽量相同，只改变一个因素，询问“如果没有 Q1 新边会怎样”。M 组就是对新边的反事实遮罩。

#### bootstrap confidence interval（自助法置信区间）

从现有 blocks 有放回抽样，重复计算均值，估计差值可能落入的范围。它不制造新信息，只描述当前样本的不确定性。

#### sign test（符号检验）

只看每个配对差值是正、负还是零，不假设分布形状。Stage 5 的确定性差值全部为零，因此 `p=1`。

#### mechanism check（机制检查）

不仅看最终分数，还检查中间机制：新边是否进入路径、是否触及必需 Episode、遮罩是否改变排名、是否改变最终证据组覆盖。

#### marginal contribution（边际贡献）

加入一条边后，相比不加入它，指标增加了多少。边被遍历不等于有边际贡献；如果它只连接本来就会被选中的节点，贡献可能为零。

## 4. 数据库与内存架构

### 4.1 为什么使用 SQLite

当前采用 Python `sqlite3 + SQLite`，原因是：

- 单机个人实验部署简单；
- 事务、索引、外键和 BLOB 已足够；
- 数据可直接检查和备份；
- 当前写入并发不高；
- 不必过早引入独立数据库服务。

SQLite 是持久化真相，EmbeddingIndex 和查询缓存都可以重建。

### 4.2 当前核心表

除 Source/Episode/Concept/Association 外，还实现了：

- `extraction_run`：一次导入运行的配置、提示词版本、日志和总结；
- `extraction_task`：每个 Source 分片在每个处理阶段的状态、模型、重试和错误；
- `concept_alias`：Concept 的多语言别名。

这不是额外的专家系统，而是可复现性和失败分析所需的运行元数据。

### 4.3 Episode 的重要字段

```text
source_id          回查 Source 原文
source_key         逻辑文件名
segment_index      所属分片编号
text               Episode 自然语言文本
participants_json  参与者
event_type         事件类型
location_text      地点描述
story_time_text    原文中的时间描述
story_order        推断出的故事发生顺序
timeline_scope     时间线适用范围
confidence         提取置信度
embedding          float32 BLOB
```

`story_order` 服务于倒叙中的实际时间恢复；它不把叙述顺序当最终事实。没有可靠时间时允许为空。

### 4.4 Episode 与 Concept 为什么分两个 index

虽然两者使用同一 embedding 模型，但数据库 ID 空间独立：`Episode.id=17` 和 `Concept.id=17` 可以同时存在。

分离索引的优点：

- 大多数操作天然只搜索一种节点；
- ID 不需要包装成 `("episode", 17)`；
- 可分别调整 Top-K 和容量；
- 统一搜索时分别检索后再融合即可。

这不妨碍跨 Episode/Concept 联想，因为图的端点已经带 `from_type/to_type`。

### 4.5 预分配、扩容与并发

EmbeddingIndex 使用：

```text
ids:        (capacity,) int64
embeddings: (capacity, 1024) float32
count:      已写入元素数
capacity:   已分配槽位数
```

搜索只能读 `[:count]`；未使用的 `np.empty` 区域不能参与计算。

追加顺序必须是：

```text
写 ids[i]
写 embeddings[i]
最后发布 count += 1
```

扩容时申请两块新数组、复制 `[0:count]`、再原子替换数组引用。第一版可以让追加、删除和扩容持写锁；搜索开始时短暂取得数组引用和 count 快照，然后释放锁做矩阵乘法。旧数组引用仍被 reader 持有，因此扩容不会破坏正在进行的搜索。

### 4.6 删除策略

当前索引采用 O(dimension) 的 swap-delete：

```text
删除位置 i
→ 把最后一个有效元素搬到 i
→ 更新 id ↔ index 映射
→ count -= 1
```

这样不需要移动后面所有行。数据库删除先完成，再更新 RAM；若中途崩溃仍可重建。

### 4.7 SQLite 连接生命周期

不共享一个长期全局 cursor。每个操作通过连接工厂取得自己的 connection/cursor，并启用 WAL、`busy_timeout` 和短事务。

原因是：

- Python sqlite connection/cursor 默认不适合跨线程共享；
- 长事务会阻塞写入和 checkpoint；
- cursor 是一次查询的迭代状态，不应成为全局服务状态。

如果未来 Telegram 查询和导入并发，应使用“每协程/线程一次短连接或连接池”，而不是依赖 `check_same_thread=False` 共享同一个 cursor。

## 5. 导入、清洗与提取设计

### 5.1 输入兼容层

当前支持 TXT 和 JSON。蔚蓝档案 JSON 通过适配器转换成统一的 `NormalizedBlock`，再交给分片器。

清洗原则：

- 清除控制符、富文本和无意义命令；
- 保留中文、日文、英文等多语言内容；
- 保留原始人物标记和不确定说话者；
- 不擅自把 `[USERNAME]` 替换成“老师”；
- 可以通过后续 Concept/Association 学会 `[USERNAME]` 与老师的关系；
- `ScriptKr` 等字段只作为人物识别线索，不能覆盖实际对白证据。

### 5.2 Source 分片

配置：

```text
target_chars   = 6000
max_chars      = 8000
overlap_chars  = 800
minimum_blocks = 2
```

设计原则：

- 优先在对话和记录的自然边界结束；
- 6000 是目标，不是机械硬切点；
- 8000 是软上限，完整记录可能轻微越界；
- 相邻 Source 保留完整记录级重叠上下文；
- 不把一句长记录从中间截断。

冻结基线的实际分布：

| 数据 | min | p50 | p95 | max | mean |
|---|---:|---:|---:|---:|---:|
| Source 字符数 | 1000 | 5909 | 7990 | 8059 | 5904 |
| Episode 字符数 | 11 | 71 | 160 | 284 | 78.5 |
| 每 Source 的 Episode 数 | 2 | 5 | 9 | 12 | 5.03 |

现有 Source 长度基本符合设计。少量 11 字符 Episode 应个别审计，不应据此把所有 Episode 整体加长。

### 5.3 Episode 提取原则

当前提示词把“可回想的事件阶段”作为单位，而不是固定句数：

- 同一时间、地点、目标和连续互动尽量合并；
- 一个片段包含多个明显阶段时拆成多个 Episode；
- 当前叙事、倒叙、角色转述和推论分开；
- “曾见过”“知道存在”“建立联系”“正式认识”是不同事件；
- 摘要和推论分离；
- 不确定身份原样保留；
- 通常中文 80—300 字、15—30 条短对白生成 3—6 条 Episode，但都是软范围。

提取失败会重试；仍失败时可切换模型，并把 prompt、模型响应、错误和重试过程写入日志。导入不会因单个分片失败而全部停止，而是继续处理并汇总失败。

### 5.4 Concept 提取与去重

Concept 不限制为传统实体。每个普通 Episode 通常提取 2—6 个，但允许 0 个，避免为凑数制造“事情”“交流”等泛节点。

去重设计是：

```text
向量相似度给候选
→ LLM 判断语义是否相同
→ 相似但不确定时先建立关系
→ 后续用户交流或新证据确认
→ 达到条件后合并 canonical concept
```

这里故意不使用单一余弦阈值自动合并，因为跨语言、角色化名和“老师/老师职业/某人的老师”等语义边界需要上下文。

### 5.5 提取版本与日志

当前提示词版本为：

```text
v3.21_atomic_coverage_source_audit
```

数据库保留最新有效提取结果，旧模型完整输出、提示词和错误进入 JSONL 日志，便于比较和复盘。人工修订程序可以查看模型返回、修改相关内容，并记录操作。

## 6. 查询与 Association 增长的完整流程

### 6.1 当前查询配置

```text
episode_top_k                         = 40
concept_top_k                         = 20
candidate_limit                       = 600
graph_max_hops                        = 3
graph_beam_width                      = 20
growth_max_rounds                     = 2
growth_episode_limit                  = 40
answer_episode_limit                  = 30
answer_concept_limit                  = 20
answer_path_limit                     = 24
answer_whole_question_anchor_episodes = 10
answer_anchor_episodes_per_query       = 6
source_excerpt_chars                  = 3000
```

### 6.2 查询阶段

```text
用户问题
  ↓
QueryIntent：识别人、事、时间、限制与证据槽
  ↓
完整问题 + 原子查询分别做 Episode/Concept 向量检索
  ↓
RRF 融合、保留全题锚点和每个原子查询锚点
  ↓
从这些 seed 沿现有 Association 最多遍历 3 跳
  ↓
根据缺失槽生成 follow-up queries，再检索一次
  ↓
合并成最多 600 条候选
```

### 6.3 增长阶段

```text
最多 40 条增长证据
  ↓
DeepSeek 生成候选 Association
  ↓
本地结构检查
  ↓
DeepSeek 证据审计
  ↓
GLM 对抗审计
  ↓
两者都接受才写入 SQLite
  ↓
新边立即参与下一轮图遍历
```

增长允许连接远距离片段，但必须遵守：

- 至少一端是 Episode；
- 跨 `source_key` 默认不是同一现场；
- 历史支援只能写成背景，不能凭空升级为具体渗透机制；
- 角色推测仍是推测；
- 问题中的暗示不是证据；
- 无证据的因果和身份边必须拒绝或降级。

### 6.4 回答阶段

最终从候选中选出最多 30 个 Episode、20 个 Concept 和 24 条路径，并附带 Source 摘录。回答器必须区分：

```text
明确事实
角色说法或角色推测
跨片段推论
仍未确定
```

答案完成后，审计器逐主张检查人物身份、主客体、时间、因果和 Source。强因果问题还有跨事件连续性审计，防止把早期行动、长期联系或防御缺口误写成后一次事件的具体机制。

### 6.5 当前提示词与代码合同的不一致

提示词希望初始原子查询为 3—8 个、follow-up 为 2—6 个；但当前 `QueryIntent.from_dict` 最多保留 4 个 search queries，follow-up 规划代码也最多保留 4 个。

Stage 5 每次 replay 实际观察到：

```text
初始检索 = 完整问题 1 个 + 原子查询 4 个
follow-up = 4 个
```

这属于实现合同不一致。修复时必须同时考虑 30 条证据预算，否则单纯增加查询数可能产生更多锚点竞争，反而降低最终覆盖。

## 7. 为什么统一使用 float32

### 7.1 设计决策

磁盘和 RAM 统一使用 `float32`，不再实施“float8 粗召回 + float16 精排”。

主要理由：

- NumPy/CPU 对 float32 矩阵乘法支持成熟；
- float8 常需要转换或由库内部提升精度，理论 1 byte/element 不等于实际更快；
- 两阶段检索会增加 SQLite 回读、dtype 转换和召回损失评测复杂度；
- 当前 32 GiB RAM 足以支撑早期验证；
- 本阶段实测瓶颈在远端模型，不在本地向量扫描。

### 7.2 本地实测

测试条件：8 核 CPU、32 GiB RAM、无 GPU、1024 维、Top 100。

| 向量数 | float32 矩阵内存 | 平均查询耗时 |
|---:|---:|---:|
| 100,000 | 0.381 GiB | 8.44 ms |
| 1,000,000 | 3.815 GiB | 86.31 ms |

如果 Episode 和 Concept 都各有 100 万条，两个矩阵约 7.63 GiB；再加 IDs、预分配余量、SQLite cache 和程序内存，仍在 32 GiB 环境可规划范围内。

### 7.3 何时才应引入 ANN 或量化

只有出现以下证据时才调整：

- 实际向量规模导致 RAM 接近上限；
- 本地向量搜索在端到端延迟中占主要比例；
- 连续查询吞吐确实不足；
- benchmark 证明量化/ANN 在可接受 recall 损失下显著更快。

目前没有这些证据，因此 float32 brute-force 是更清晰、更可靠的实验基线。

## 8. 实验路线如何逐步发展

### Stage 1：数据和向量主链

目标是证明输入适配、Source 分片、Episode/Concept 提取、float32 BLOB 编解码、RAM index、SQLite 回查和 Telegram 查询入口能够运行。

### Stage 2：封闭语料深度题

通过“补习部真相”“乐园悖论政治投影”“古圣堂袭击因果链”等问题，检查远距离片段是否能在同一答案中闭环。此阶段发现，答案失败往往不是向量完全没找到，而是原子查询或最终证据预算没有覆盖所有槽位。

### Stage 3：安全增长闭环

为 Association 增加 `claim_level`、溯源快照和双模型审计，扩大增长证据池，并实现 fail-closed 写入门。冻结出 Stage 3 基线。

### Stage 4：更难的网络联想题

在 11 个封闭文件中设计 7 道需要 7—9 组证据的问题，比较：

| 模式 | 语义通过 | 精确 Episode 组覆盖 |
|---|---:|---:|
| vector only | 7/7 | 49/56 |
| graph static | 7/7 | 44/56 |
| graph growing，原顺序 | 7/7 | 52/56 |
| graph growing，反向顺序 | 7/7 | 50/56 |
| graph growing，交错顺序 | 7/7 | 51/56 |

这证明增长图可以安全使用，也显示题序会改变路径。但是，Stage 4 还不能证明“增长边导致了更好结果”，因为各模式的查询规划和生成都可能不同。

### Stage 5：Association 的因果贡献

Stage 5 不再问“能否写边”，而是问：

> 当 Q1 学到一批关系后，这批关系是否会让后续 Q2 覆盖更多预先指定的正确证据？

这需要反事实、配对和确定性 replay，因此比简单比较两个答案严格得多。

## 10. Stage 5 实验设计

### 10.1 四个实验臂

每个 official block 都从同一冻结基线的独立副本开始：

| 组 | Q1/Q7 操作 | Q2 时看到的图 | 用途 |
|---|---|---|---|
| T | Q1 graph-growing | 包含 Q1 新边 | 处理组 |
| C | Q1 graph-static | 没有 Q1 新边 | 基础对照 |
| M | 从 T 的 Q1 后 DB 派生 | 读取时隐藏 Q1 created，恢复 reinforced 旧行 | 直接反事实遮罩 |
| P | 无关 Q7 graph-growing | 包含无关增长边 | 安慰剂对照 |

### 10.2 AssociationDelta

`AssociationDelta` 记录 Q1 前后 Association 的完整变化：

- created：新增 ID 与完整新行；
- reinforced：同一 ID 的 before/after 完整行。

它比只记录边数更重要，因为可以精确重建“Q1 改了什么”。

### 10.3 AssociationOverlay

`AssociationOverlay` 是只读视图：

- `neighbors/get/list_temporal` 会过滤 created IDs；
- reinforced IDs 返回 Q1 前的旧行；
- `mark_used` 是 no-op；
- upsert/delete 被禁止；
- 原处理组 SQLite 不被修改。

因此 M 与 T 的其他状态相同，只在 Association 可见性上不同。

### 10.4 两层评测

#### 第一层：确定性 replay（主要因果证据）

- 问题；
- QueryIntent；
- 初始与 follow-up queries；
- float32 query embeddings；
- Episode/Concept 排名；
- seeds 和 atomic anchors；
- 检索配置。

Replay 不调用 LLM、不增长边、不更新 `use_count`。组间差异只能来自 Association 视图。

#### 第二层：完整端到端（真实使用表现）

每组独立完成规划、检索、回答和审计。它可观察真实系统表现，但不能把所有差异归因于图，因为 LLM 输出和网络重试会产生噪声。

## 12. 为什么“路径被复用”仍没有提升

### 12.1 Q1 新边多为解释性冗余

处理组共创建 75 条边，安慰剂组创建 73 条，没有强化旧边。处理组常见关系包括：

```text
evidence_bridge       25
thematic_contrast     19
thematic_response     12
historical_context     5
role_evidence_bridge   4
```

典型 Q1 路径：

```text
274 ↔ 84   原 ETO 的政治目的 ↔ 古圣堂签署/成立仪式
123 ↔ 84  第一次公会议与戒律守护者 ↔ 原 ETO
123 ↔ 198 古圣堂历史 ↔ 废墟上的新 ETO
199 ↔ 198 老师代理发起人 ↔ 新 ETO 宣告
```

这些边合理且可解释，但端点本来已经很容易被 Q2 召回。它们让已有证据之间的解释更连贯，却没有带来新的证据组。

### 12.2 召回不是瓶颈，Top-30 分配才是

每个 block 的 600 条候选都覆盖 8/8 证据组。最常丢失的是第 5 组 `[139,140]`：阿里乌斯的具体作战部署。

该组在候选中的首次位置约为 13—33，10/10 都存在；Episode 140 还经常由图扩展带入。但最终 30 条中该组仍可能完全缺失。

这看似矛盾，原因是“候选排名”不是最终证据选择的唯一顺序。当前分配器先保留大量原子锚点，再加入路径端点，最后才按全局得分填充。

### 12.3 当前配额的具体影响

`answer_episode_limit=30` 时：

```text
base_quota = (30 × 3) // 4 = 22
```

前 22 个位置优先由完整问题和原子查询 anchors 占据。然后才考虑路径端点和剩余高分候选。

在部分 blocks 中，139/140 只作为第 26 或第 30 个原子 anchor 出现，因此没有得到保护。与此同时，Q1 新边带来的历史桥通常又连接已覆盖端点，占用了有限路径位置。

因此当前失效链是：

```text
正确证据已进入 600 候选
→ 原子锚点重复占用前 22 个槽
→ 解释性路径带来已有证据
→ 139/140 未进入最终 30
→ Recall 停在 6/8 或 7/8
```

### 12.4 对“自主增长”的真正含义

Stage 5 说明边数量不能代表神经网络式成长。更有价值的增长应至少满足一种效果：

- 把原本不在候选中的正确记忆召回；
- 把候选尾部的关键 Episode 推进最终证据集；
- 用一条路径替代多条冗余路径，释放预算；
- 让缺失证据槽更早被识别并产生有效 follow-up；
- 在同等证据下提高事实/推论边界的稳定性。

只连接两个本来就会出现的高排节点，属于“解释性复用”，不等于检索增益。

## 15. 当前技术问题及其优先级

### P0：最终 30 条证据的分配算法

正确证据已经召回，却被 anchor/path 配额裁掉。继续扩大候选或写更多边不能直接解决。

### P0：Association 的边际贡献评估

目前能看到“边被使用”，但还需要逐边遮罩，判断哪条边改变了排名、证据组或 follow-up。否则图会积累大量合理但无增益的解释性边。

### P1：查询提示词与代码上限不一致

3—8 个原子查询和 2—6 个 follow-up 的提示词合同，实际被代码截成 4/4。应统一配置和测试。

### P1：答案边界结构不稳定

LLM 已理解事实/推论/未知，但不总打印一致标签。应由确定性渲染器检查和补齐结构，不必再增加一次昂贵 LLM 调用。

### P1：API 长尾与超长 prompt

答案和审计占绝大多数时间。需要减少重复 Source、对相同证据做缓存、让审计只看具体主张所需片段，并保留 fail-closed。

### P2：增长边偏局部、偏冗余

当前候选生成容易建立“主题承接”和“历史背景”边，但难以生成能把低排关键证据带入预算的桥。需要把“检索增益”作为后验维护信号，而不是降低证据审计门槛。

### P2：实验外推范围有限

Stage 5 只有一个主要 Q1→Q2 因果配对和 10 个 blocks。结果能否推广到其他人物、跨模块情绪联想或长期用户记忆，仍需复制实验。

## 16. 下一阶段实验路线

### 16.1 第一阶段：完全离线的 evidence allocator 消融

复用现有 10 个 replay bundles，不调用 API、不修改数据库，比较：

1. 现有算法：最多 22/30 先给 anchors；
2. anchor 总上限 15/30，其余先按全局 score；
3. 每个原子查询只保护 1—2 个“独占且未覆盖”的 anchor；
4. 证据组/来源多样性约束，减少同义 Episode 重复；
5. path endpoint 只在补充新槽时得到优先权；
6. 最后用全局分数补满 30 条。

主要指标仍是 8 组 `Recall@30`，尤其检查 `[139,140]`。边数不参与评分。

建议同时记录：

```text
每个候选的进入来源
每个 anchor 占用原因
被裁掉的首个必需 Episode
同一证据槽的重复数量
图端点是否补充新证据组
```

### 16.2 第二阶段：逐边反事实贡献

对实际进入 Q2 路径的每一条 Q1 delta 单独遮罩，测量：

- Episode 排名变化；
- 是否只是同组等价替换；
- 是否把 candidate-only Episode 推入 Top-30；
- 是否减少路径冗余；
- 是否改变 follow-up 查询；
- 是否改变最终答案的事实完整度。

把结果分成：

```text
retrieval-useful      改善证据覆盖
explanation-useful    不改覆盖，但提供可解释路径
redundant             没有可观察作用
harmful               挤掉更关键证据或引入错误方向
```

这只是后验维护标签，不应把“没有立即提分”的边自动删除；人的记忆允许弱联想。但系统可以据此调整路径预算和权重。

### 16.3 第三阶段：统一查询合同

把初始原子查询和 follow-up 上限移动到配置中，并增加合同测试。建议先做 4/4、6/4、8/6 三组离线或低成本比较，同时固定总 anchor 预算，避免查询越多、重复越多。

### 16.4 第四阶段：固定答案结构

输出固定四段：

```text
1. 明确事实
2. 角色说法或推测
3. 跨片段推论
4. 仍未确定
```

生成后由本地程序检查四段是否存在，并附加确定性的 Source 清单。内容审计继续由模型完成；格式完整性由程序保证。

### 16.5 第五阶段：复制因果实验

在不同类型的问题上至少增加三类 Q1→Q2：

- 身份/化名链：人物—组织—代号—喜好；
- 时间线链：倒叙、第一次见面、后来正式认识；
- 情绪触发链：当前场景为什么唤起旧创伤；
- 跨模块政治/人物链：主线与活动剧情间的真实出现和类比边界。

每一类都要预注册证据组、处理/遮罩/对照，防止只对古圣堂问题过拟合。

### 16.6 第六阶段：长期增长与退化测试

在因果贡献出现后，再进行连续数小时或数天的增长实验，观察：

- Association 数量和类型分布；
- 同一节点的度数是否爆炸；
- 重复、冲突和否定边；
- 旧边的 reuse 与 marginal contribution；
- 人工反馈后能否修正；
- 删除 Episode 后边和内存索引是否一致；
- 数据库大小、重建时间和查询延迟。

## 17. 发展成实际系统时的设计原则

### 17.1 不把 Association 当作真相

Association 是联想线索，最终回答仍必须回到 Episode 和 Source。强边也不能覆盖原文。

### 17.2 允许模糊，但必须保留边界

人的记忆会模糊，因此可以保留弱关系、无明确类型关系和角色推测；但系统必须知道它们不是直接事实，并在答案中说明不确定性。

### 17.3 新连接要可追溯

每条自主增长边都应知道端点、原文、模型、提示词、审计和时间。否则长期增长后无法修正。

### 17.4 图的价值看后续作用，不看体积

边数量增长只是状态变化。真正价值包括检索新证据、减少搜索步骤、形成解释路径、支持新推论或帮助发现未知。

### 17.5 避免过早专家系统化

关系信息尽量保存在通用 Association 的 `relation_type/key/text` 中，而不是为每种剧情机制建立专表。只有某个结构在多轮实验中证明稳定必要，才升级为专门数据结构。

### 17.6 先建立精确基线，再优化速度

float32 brute-force、SQLite 和详细日志目前让错误可观察。ANN、量化、分布式服务应由真实瓶颈触发，而不是由百万级估算提前触发。

这个 demo 已经越过“简单 RAG”的阶段：它拥有事件记忆、广义 Concept、多语言别名、向量搜索、图遍历、查询期增长、双模型审计、原文回查和反事实实验工具。

Stage 5 给出了一个重要的负结果：

> 新 Association 确实被后续检索使用，但当前形式没有提高预注册证据组覆盖。

这个负结果是有价值的，因为它把问题定位到了更具体的层次：

```text
不是 embedding 没找到；
不是 float32 太慢；
不是新边没被遍历；
不是安全门阻止了一切增长；
而是正确证据已经进入候选后，最终 30 条的分配与边的冗余性没有产生边际收益。
```

因此下一步推荐顺序是：

1. 用现有 replay bundles 离线改证据分配器；
2. 对 Q1 新边做逐边反事实贡献分析；
3. 修复原子查询/follow-up 的提示词与代码合同；
4. 固定事实、推测、推论、未知四段输出；
5. 在身份、时间线、情绪和跨模块问题上复制因果实验；
6. 只有在出现真实容量或延迟证据后，再考虑 ANN、量化或更复杂数据库。

这条路线既保留系统“像人一样不断形成联想”的目标，也避免把图的自然增长误当成能力增长。下一阶段真正要证明的，不是系统能写多少条边，而是：

> 它新形成的某条联系，能否在未来某个问题上稳定地帮助想起原本会漏掉的关键记忆，并且仍能说明这条联系来自哪里、可靠到什么程度。

## 20. Stage 6 追加设计：Paragraph 与细粒度 Concept

用户提出在 Source 与 Episode 之间加入 Paragraph 原文 embedding，并更积极、细粒度地创建 Concept。该建议已转换成可独立开关、可消融、可回退的实现，不直接改变 Stage 5 历史结论。

### 20.1 Paragraph 的作用

Paragraph 是按完整 dialogue record 组成的约 900—1600 字原文块。它用于补偿 Episode 摘要可能省略专有词、具体部署和局部措辞的问题。

Paragraph 不加入 Association 图。命中后，系统找到相同 `source_id` 的 Episode，用 query 向量在该 Source 内局部精排，再以 0.35 倍 RRF 权重加入 Episode seeds。因此它是原文召回辅助通道，不会形成第三种图节点。

冻结库只读估算会生成 541 个 Paragraph，float32 embedding 约 2.11 MiB。该规模几乎不构成 RAM 压力。

### 20.2 Concept 的新档位

- `conservative`：恢复 Stage 5 前的 2—6 个高复用概念策略；
- `fine_grained`：软目标 4—10 个，积极检查参与者、化名、制度、命名事件、地点子区域、关键物品、持续心理和抽象主题。

细粒度档仍禁止制造一次性动作、复合事实节点、重复多语言节点和外部知识。

### 20.3 回退方式

```text
MEMORY_PARAGRAPH_ENABLED=0
MEMORY_CONCEPT_PROFILE=conservative
```

Paragraph 表可保留但不参与查询。Concept augmentation 只允许在冻结库副本上进行；回退时直接使用未 augmentation 的基线副本。

### 20.4 当前证据状态

schema、分片、回填、索引、查询融合、Concept 双档和 77 项本地测试已经完成。但正式 A/B/C/D 剧情消融尚未执行，所以当前只能确认实现可用和可回退，不能宣称它提高了实际 Recall。

完整实验计划见 `STAGE6_PARAGRAPH_CONCEPT_EXPERIMENT_PLAN_2026-08-26.md`。

## 21. Stage 7 追加结果：generation、放宽审计与增长收益复核

Association 已增加 `generation INTEGER`，用于独立表示推断距离：0 为直接经验关系，1 为直接证据上的首层推论，继续使用已有推论时取 `max(前提 generation) + 1`。`confidence` 继续只表示可信度。同一关系强化时保存最小 generation，所有推导证据仍合并留存。

增长模型现在必须用 `premise_association_ids` 明示所使用的已有推论边；引用不可见边会被拒绝。双模型审计仍保留，但不再因“不是原文逐字陈述”而默认拒绝合理、受限、可追溯的推论。Paragraph 默认关闭，Concept 恢复 conservative，避免混杂。

81 项回归测试通过。一次在线四臂 pilot 中，T 创建 8 条 generation 1 边，答案安全审计全部通过。固定 replay bundle 四臂均为 8/8，出现天花板；完整 Q2 的 T/C/M/P 分别为 6/8、7/8、6/8、7/8，T-M 为 0。把同一 delta 重放到 10 个冻结 bundle 上，新边在 9 个 bundle 中被使用、7 个 bundle 中改变排序或选择，但 T-M Recall 差仍全部为 0。

16 个单边双向端点探针中，4 个增加 candidate 可达性、5 个增加最终选择可达性。这说明边具有局部检索作用，却尚未转化为预注册真实问题的稳定净收益。当前结论仍是负结果，不能宣称增长收益通过。

完整定义、表格、限制与资产见 `EXPERIMENT_REPORT_STAGE7_GENERATION_2026-08-26.md`。
